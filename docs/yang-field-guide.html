YANG Studio · orientation

YANG, from inside the app you're building

Every example here is real output from a Cisco IOS-XE device. Nothing is invented.

The one idea: YANG is a schema language, not a protocol.

A .yang file describes what data a device holds — the shape of the tree, the type of every leaf, which parts are configurable. It says nothing about how you read or write that data. NETCONF, RESTCONF and gNMI are three transports that all carry the same tree.

This is why your instinct was right. Learning YANG is the transferable part; the protocol is the easy skin on top.

01 What comes back when you press Connect

A NETCONF session opens with both sides announcing what they support. Your CSR sends back 522 capability strings: 15 describing the protocol itself, and 507 describing YANG modules.

Here is one of those 507, exactly as it arrived:

urn:ietf:params:xml:ns:yang:ietf-interfaces?module=ietf-interfaces&revision=2014-05-08 &features=pre-provisioning,if-mib,arbitrary-names &deviations=cisco-xe-ietf-ip-deviation
namespace
The module's globally unique identity. Every node in its tree lives under this — it's what the xmlns in a NETCONF request points at.
module
The module's name. This is the thing you download.
revision
Which dated version the device implements. Modules change over time; this pins it.
features
Optional parts of the module the device actually implements. Everything else defined behind a feature flag is not on this box.
deviations
Where the vendor departs from the standard module — nodes unsupported, ranges narrowed. Named modules that themselves must be downloaded.
The critical part: this is a promise, not the schema. The device is saying “I implement ietf-interfaces at this revision.” It has not sent you the model. You still don't know what's in it.

02 What you're downloading

Pressing Download issues a separate NETCONF request per module — <get-schema> — and the device returns the module's source text. That text is the schema. It's human-readable, and reading it is the fastest way to understand YANG.

This is the real ietf-interfaces the device returned, trimmed:

container interfaces {          // a fixed node — exists once
  list interface {             // repeats; one entry per interface
    key "name";                // what makes each entry unique

    leaf name {                // a single value...
      type string;             // ...of this type
    }
    leaf description {
      type string;
    }
    leaf enabled {
      type boolean;
      default true;
    }
  }
}

Four keywords carry most of YANG. container groups. list repeats and needs a key. leaf holds one typed value. Everything else is refinement.

That structure is exactly what the tree in the Explore page is drawing. When you click a node, the panel is showing you fields lifted straight out of this text.

03 Why it asks for other modules too

Modules are not self-contained. They borrow types and definitions from each other, and they say so at the top:

// in ietf-ip.yang, line 7
import ietf-inet-types {
  prefix inet;               // refer to it as "inet" below
}

// line 176 — the borrowed type in use
leaf address {
  type inet:ipv4-address-no-zone;
}

What is an ipv4-address-no-zone? Nothing in ietf-ip answers that. The definition lives in the other file:

// in ietf-inet-types.yang, line 193
typedef ipv4-address {
  type string {
    pattern '(([0-9]|[1-9][0-9]|1[0-9][0-9]|2[0-4][0-9]|25[0-5])\.){3}'
          + '([0-9]|[1-9][0-9]|1[0-9][0-9]|2[0-4][0-9]|25[0-5])';
  }
}

So without ietf-inet-types, the parser genuinely cannot tell you what that leaf accepts — no type, no validation pattern, no help when you fill in a value. That's the entire reason the app offers to fetch the imports: a module without its dependencies is an incomplete schema, and pyang refuses it.

This is what “Will not parse yet — 4 imports missing” means. It's not the app being fussy. It literally cannot build the tree.

04 Why a repository and a set

This is the distinction that trips everyone, and it's worth being precise, because they answer different questions.

Repository

“What files do I have?”

A directory of .yang files. An inventory. It can hold the same module at several revisions, and modules that flatly contradict each other. That's fine — a filing cabinet isn't required to be consistent.

Set

“Which modules resolve into one valid tree?”

A named selection: specific modules, at specific revisions, that parse together. This is the unit you explore and query. It must be internally consistent.

Why a repository can't just be parsed whole — two measurements from your own data:

What was parsedModulesResult
Every BFD module together355 errors — they all augment the same routing path and collide
One BFD module90 errors, 250 nodes

On top of that, 23 module names in the IETF collection exist at two different revisions. A tree can only use one. So there is no such thing as “the tree for this repository” — a set is what makes a tree possible at all.

You should rarely build a set by hand. Download from a device and the app offers to make one; or press Make set on the capabilities panel and it builds one from what the device advertises — including those features and deviations, which the files alone can't tell you.

05 What a set gets you

Parsing a set produces the tree in the Explore page. Every node carries two things that matter for actually doing work:

A path that addresses it

/if:interfaces/if:interface/if:description

This is how you point at one piece of data. It's the same path every protocol uses — it just gets dressed differently on the wire.

Whether you can write to it

YANG marks operational data with config false. The app shows this as a badge on every node:

BadgeMeaningExample on the device
configYou can read and write itinterface/description
stateRead-only — the device reports itinterface/oper-status

Trying to write a state node is one of the most common early mistakes. The tree tells you before you try.

And features actually narrow it

Because the device told us it implements pre-provisioning, if-mib, arbitrary-names and nothing else, a device-built set prunes what isn't there. On the device that removed if-index and link-up-down-trap-enable — 177 nodes to 174. Small here; on a full Cisco native model it's the difference between a schema and a schema that matches the box in front of you.

06 From node to request

Tick a node in the tree and the app composes a request. The path is the constant; the protocol is the wrapper. Same leaf, two transports:

NETCONF

<get-config>
  <source><running/></source>
  <filter>
    <interfaces xmlns="…ietf-interfaces">
      <interface>
        <name>GigabitEthernet1</name>
        <description/>
      </interface>
    </interfaces>
  </filter>
</get-config>

RESTCONF

GET /restconf/data/
  ietf-interfaces:interfaces/
  interface=GigabitEthernet1/
  description

Accept: application/yang-data+json

The list key becomes a path segment. The module name qualifies the top container. Same tree.

NETCONF keeps one advantage worth knowing: a candidate datastore. You stage changes, validate, then commit as one transaction — with confirmed-commit to auto-roll-back if you lose the box. RESTCONF has no equivalent. Your CSR has candidate enabled, so both are available to you.

07 The vocabulary, in one place

Everything you'll meet in the tree. The first four are ninety percent of it.

container
Groups other nodes. Exists once. A folder.
list
Repeats — one entry per interface, per neighbour. Needs a key.
leaf
One typed value. The actual data.
leaf-list
A leaf that holds several values of the same type.
key
The leaf that makes a list entry unique. Becomes the path segment when you address one entry.
config false
Read-only operational state. Shown as state.
typedef
A named, reusable type — often with a validation pattern or range. Frequently in another module.
identity / identityref
An extensible enumeration. interface/type is one — it resolves to every type derived from it, 273 of them in the IETF collection.
feature
An optional part of a module. The device says which it implements; the rest isn't there.
deviation
A vendor's documented departure from a standard module.
augment
One module adding nodes into another's tree. Powerful, and the reason modules can collide.
choice / case
Mutually exclusive alternatives — only one branch can be present.
rpc / action
An operation you invoke, not data you read. Has input and output.
notification
An event the device can push to you.
import / include
Borrowing from another module / assembling a module from submodules.
prefix
The short alias for a namespace, seen throughout paths: if:interfaces.

08 The flow, restated

With the concepts in place, the pipeline stops looking arbitrary:

StepWhat's really happening
ConnectDevice lists the modules it implements, with revisions, features and deviations. No schemas yet.
DownloadFetch the actual .yang source for the modules you chose, one request each.
RepositoryWhere those files land. An inventory — allowed to be inconsistent.
SetA consistent selection that parses into one tree. Imports resolved, one revision each.
ExploreBrowse the tree, read types and constraints, pick nodes.
RequestSelected paths become a NETCONF or RESTCONF call against the live device.
